### EHCI USB storage: write errors are not recovered (fixed in the host tests)

Seen first in USB Loader GX on the bench Wii (2026-10-23): through cIOS a sector read takes 1 ms, but a single-sector write takes 20 s to several minutes. Items 1 to 9 are fixed; 1 to 3, 5 and 6 pass host tests against the simulated drive.

**Outcome on hardware (2026-10-24):** the slow writes were that drive, a SanDisk "USB 3.2Gen1" flash drive, not d2x. On a second drive (a Memorex TF20) every build writes correctly: 272 pattern sectors written and read back, 0 mismatches, on both upstream and this branch. On the SanDisk every build fails, the old v65535 cIOS included (its lone FSInfo rewrite never returned): the drive takes the data packet, works for about 135 ms, STALLs the CSW and never sends one, and what lands on the disk is stale (the CBW bytes, or an earlier write's data). The DMA address and length were checked correct in the debug log, and the drive writes fine from Windows (xHCI), so it is an incompatibility between that drive and tinyehci at USB 2.0 high speed. A debug build's retry after a reset recovery wrote the CBW into a FAT32 root-directory sector there and hid two folders; repaired with `tools/fat32_repair_live.py`. See "SanDisk 3.2Gen1" under Still open.

| Kind | Change | Check |
| --- | --- | --- |
| Fix | **6. Clearing a halt left the host's data toggle as it was.** `USB_ClearHalt()` (`tinyehci/usb.c`) sent CLEAR_FEATURE(ENDPOINT_HALT), which resets the device's toggle to DATA0 (USB 2.0 9.4.5), but tinyehci starts each bulk transfer from the toggle in `ehci_device.toggles` (`ehci_do_urb()` in `ehci.c`), which only a port or device reset zeroes. After every Bulk-Only reset recovery, the next transfer on an endpoint at DATA1 was discarded by the device as a retransmission; the command then timed out (`usb_timeout`, about 4 s) into a port reset. `USB_ClearHalt()` now sets the host toggle to DATA0 too. (This was first thought to cause the slow writes; the bench showed those were one drive, see the outcome above.) | `reset_recovery_keeps_toggles_in_step`: before, 4 reads around two reset recoveries cost 3 lost transfers and 4 port resets; now none. Without this fix, `write_recovers_from_one_stall` also fails (a lost transfer and 2 port resets). |
| Fix | **1. A STALL at the data phase was retried forever.** In `__cycle()` the `continue; //reset+retry` in the inner data loop restarted that loop, not the command, so it resent to a halted endpoint. Now any short transfer ends the data phase (tinyehci reports a STALL as a short count); after a short bulk-out transfer the halt is cleared; the CSW is read, and a STALLed CSW read is cleared and read once more (BOT 5.3.3, 6.7.2, 6.7.3). A phase error (status 2) or a bad CSW gets a reset recovery. | `write_recovers_from_one_stall` (twice, at both toggle parities): succeeds with 2 clear-halts, no reset, no lost transfer, in under 100 ms of simulated time. |
| Fix | **2. The CSW status was never checked.** `__USBStorage_Write()` and `__USBStorage_Read()` tested `retval > 0 && status != 0`, but `__cycle()` returns 0 on success, so a failed command counted as done. Now `retval >= 0`; a failed command gets a REQUEST SENSE (which clears the condition) and returns `USBSTORAGE_ESTATUS`. | `write_csw_failure_is_retried`: one REQUEST SENSE, then a successful retry. |
| Fix | **3. `USBStorage_Write_Sectors()` and `USBStorage_Read_Sectors()` never gave up** (`if(retry>12) retry=12; // infinite loop`), and after a non-timeout error they stopped calling the driver but kept looping. | Fix | **5. The CBW never carried the command's length.** `USBStorage_Open()` set `ata_protocol` with `subclass != SCSI || subclass != RBC`, always true, so every CBW said 12; and the SCSI branch of `__send_cbw()` would have said 16 (`cbLen > 6 ? 0x10 : 6`) for any 10-byte command. Now `&&`, and SCSI and RBC devices get `cbLen`, the valid length (BOT 5.1, as Linux sends it). Other subclasses keep the padded 12. The comment on READ CAPACITY already noted that some drives require its 10-byte length. | `cbw_carries_command_length`: READ(10) carried 12 before, 10 now. |
| Fix | **4. A halted qTD wrote through a NULL pointer.** In `qh_end_transfer()` (`tinyehci/ehci.c`), `if(error) qtd->urb->actual_length = error;` ran after `for(qtd = ...; qtd; ...)` had left `qtd` NULL: on every STALL or transaction error it read a pointer from low memory and wrote -1 through it. The store is gone; a halted transfer still reports the bytes it moved (a short transfer), which is what callers, and the STALL handling above, see today. | Build only: the host simulation stops above `ehci.c`. Bench check pending. |
| Fix | **7. Every STALL was taken for an unplug.** A halted qTD sets USBERRINT (`STS_ERR`), and `handshake()` (`ehci.c`) answered that, outside the init and reset code (`handshake_mode` 0), with `unplug_device = 1` and `-ENODEV` (1 in tinyehci's `ehci_types.h`, so -1). `__cycle()` returns at once on `-ENODEV`, so none of items 1 to 3 ever ran on hardware: the drive was remounted (port reset, TEST UNIT READY, INQUIRY, READ CAPACITY) and the command tried again. On the bench drive every write's data phase STALLs after its first 512-byte packet (qTD token `0xC2000041`: halted, no error bits); the old code's retry loop kept remounting until one write got through (the 192 s first write below), this branch gave up after 4 tries. Now a halt on a connected port ends the transfer: a bulk transfer returns its short count, as the host model of items 1 and 2 assumed, and a control request returns the new `-EPIPE`. Disconnects (`PORT_CONNECT`, `PORT_OWNER`, `STS_FATAL`) and timeouts are unplugs as before; the init and reset code keeps `-ETIMEDOUT`. | The debug build's event log (`umsbench --log`): CBW sent, then the 32 KB data-out's handshake returned -1 within 1 ms, then a remount. With the fix the log shows the short count, the clear-halt and the CSW read. |
| Fix | **8. A CSW that never came after a clear-halt was taken for an unplug.** After clearing a STALLed CSW read, the second read timed out through `handshake()`'s unplug path. That read now runs with `handshake_mode` 1, so a timeout is `-ETIMEDOUT` and gets the BOT reset recovery (5.3.4) instead of a port reset and remount. | Debug build on the SanDisk: reset recovery, then the next command, instead of a remount. |
| Fix | **10. A drive that keeps failing held a request for close to a minute.** With 10 reset recoveries per command (`USBSTORAGE_CYCLE_RETRIES`, the module build) and 4 attempts per request, each waiting out a 1 s timeout, a write whose status never came took about 48 s to fail, with 6 remounts; to a loader that is a hang. Now a sector request also stops at `USBSTORAGE_REQUEST_MS` (8 s): no new attempt or reset recovery starts after it, and the caller gets an error. A drive that is gone (unplugged) is still waited for without limit, and a request that waited through a replug starts afresh. Written up for developers in `docs/usb-storage.md`. | `write_with_lost_status_fails_in_time` (a new `lose_write_csw` fault that copies the SanDisk): 47.7 s, 43 BOT resets and 6 port resets before; 8.5 s, 7 BOT resets, no port reset now. `write_with_one_lost_status_recovers`. Bench, mr12 on the Memorex: 2 x 1088 pattern sectors, 0 mismatches. |
| Speed | **9. Every USB wait slept before its first check.** `handshake()` called `ehci_usleep(10)` before reading the status. That is an IOS timer and message-queue round trip, not 10 us, and each command makes about six such waits (CBW, data and CSW, each followed by a "controller stopped" check that is usually true at once). It now checks first, polls without sleeping for `HANDSHAKE_SPIN_TICKS` (100 Hollywood ticks, about 53 us), and only then sleeps between checks, so a long transfer still lets other threads run. | Release builds, umsbench, 3 runs each on the SanDisk (reads): 1-sector read 0.82 ms avg on mr9 to 0.66 ms (worst 5.1 to 2.5 ms); 64-sector 1.91 to 1.81 ms. On the Memorex (2 runs each, upstream vs this branch): 1-sector read 0.58 to 0.45 ms, 64-sector 1.59 to 1.49 ms; writes unchanged (flash-bound: 2.6 ms and about 3.7 ms). USB Loader GX's launch path up to WDVD_OpenPartition: 215 ms on both. |

Items 1 to 3 and 6 change only `usb.c` and `usbstorage.c`. With the build date pinned, only `EHCI.app` changes (16820 to 16836 bytes; `.text` 0x3F70 of the 0x5000 the module may use). No new compiler warnings.

Still open:

- **Report a bulk STALL as an error code.** Since item 7 a halted bulk transfer looks like a short one, so a STALL and a short packet are told apart only by direction (control requests already get `-EPIPE`). Returning `-EPIPE` for bulk halts too would let `__cycle()` follow BOT exactly, but the ioctls in `loop.c` pass bulk results to callers, which would see a new error. Trigger: a bench run that shows a drive whose short packets and STALLs are confused.

- **SanDisk 3.2Gen1: writes land stale data.** Above. Ruled out on the bench with debug-build quirks (`UMS_QUIRK_*` in `tinyehci/ums_quirks.h`, set with `USB_IOCTL_UMS_SET_QUIRKS` in `EHCI_DEBUG_LOG` builds only): the CBW length (padded 12 or the command's own 10), keeping the host toggle on a clear-halt, a PING before bulk-out, and the data on the other toggle (the drive then drops our packet as a duplicate and still writes its stale buffer, so the toggles were in step). Next step, needing a capture: record a Windows write to that drive through a USB 2.0 hub (USBPcap) and compare the packet sequence with tinyehci's. Until then: do not write to that drive through d2x. Trigger: a user report of the same drive, or another drive that fails the same way.
- **The DIP's decrypted partition read hung IOS on the bench, but not because of the dead disc drive.** USB Loader GX's bench build reading SB4E01 from the SanDisk in fragment mode (its own fragment list, built from wbfs/<Title>/<ID6>.wbfs): SetFragList, Disc_Open, FindPartition and OpenPartition worked, and the first `WDVD_Read` (0x71) never returned, on upstream d2x too. The dev Wii's disc drive is broken, which suggested the DI module waits on it. **A DIP trace build disproved that (2026-10-25, GX job 20261025-012720-7b2541):** on the same dev Wii, dead drive and all, with NSMBW (SMNE01) on the scratch Memorex through GX's own fragment list, the 32 KiB read returned in 8.4 ms with the right data. The trace shows the path: GX's 0x71 goes to Nintendo's DI module (`D 71`), which calls back into the plugin with 0xA8 reads (`C a8`), served from USB (`R`/`r`, about 1.5 ms per 32 KB), and returns (`d 71`). The physical drive is never used, so a dead or missing drive does not hang a USB launch. The earlier hang is the SanDisk (its reads, or the GX bench's fragment remap for that file); GX checks its remap when that drive is back. The trace build (`EXTRA_CFLAGS=-DDIP_DEBUG_TRACE`, `source/dip-plugin/trace.h`) stays as the tool for the next IOS hang. Trigger: an IOS hang on a known-good drive.

**Is base 58 faster than 56?** Every transfer is an IPC round trip to IOS and costs about 1 ms whatever its size (dev Wii: 64 sectors in 4 KB pieces 10002 us, in 16 KB pieces 4051 us). USBS sends 16 KB pieces, through the bounce buffer or direct for an aligned MEM2 buffer, both split at `USBS_MAX_TRANSFER` (16384; docs/usb-storage.md). **Finding (2026-11-05, dev Wii, base 58 = IOS58 v6175): a direct transfer of 65024 bytes hangs IOS.** umsbench's 64-sector read (32 KB, one direct transfer into an aligned MEM2 buffer) never returned from /dev/usb/ven, the console froze and needed a power cycle; the 8 s deadline could not help because the IPC call itself blocked. 16 KB transfers work (+usbs16: 64 sectors in 4051 us, 0 failures). The IOS58 /dev/usb/ven per-transfer limit looks like 16 KB, which matches libogc's MAX_TRANSFER_SIZE_V5; 32 KB blocked forever. So there is no separate direct size any more (`USBS_MAX_DIRECT` was removed, which also saved code in the 0x3000-byte module). Do not try a bigger transfer again without a timeout that IOS itself enforces.

**Wii plan (USBS):** install `d2x-v11-rc1-usbs` in slot 252 (base 58); confirm it survives its first sector request; then `umsbench` on the scratch drive, EHCI (base 56) against USBS (base 58), same pattern and size, read then write, 3 runs each.

Open question: USBS defines `USB_ClearHalt(id, ep)` as `USB_CancelEndpoint(id, ep)`, an IOS request that cancels an endpoint's pending transfers. Whether IOS also sends CLEAR_FEATURE(ENDPOINT_HALT) there is not visible in this code; if it does not, a STALLed endpoint stays halted after a USBS reset recovery. Left as it is on purpose: an explicit CLEAR_FEATURE sent as a raw control message would reset the device's data toggle but not the one IOS keeps for the endpoint, the mismatch EHCI item 6 fixed, and nothing here shows how IOS tracks it. Trigger: a USBS drive that stops answering after a STALL on the bench.

### SD high speed (opt-in, `SDIO_HIGH_SPEED`)

| Kind | Change | Check |

| Measurement | **What IOS does with the SD clock (ironic, running the real IOS from the dev Wii's NAND, 2026-11-04).** d2x's SD path (`cios-lib/sdio.c`) uses IOS's `/dev/sdio/slot0` ioctls: WRITEHCREG 1, READHCREG 2, SETCLK 6, SENDCMD 7. `SETCLK(n)` writes the clock control (0x2c) divisor field: clock = base / 2n, n = 0 the undivided base. d2x calls `SETCLK(1)`: base / 2. ### Module size headroom (opt/size, 2026-11-05)

Every module is Thumb, `-Os`, `-ffunction-sections`, `--gc-sections` already, so there was no compiler flag left to gain from; the gains came from code that was linked and never needed. The `exe` regions in each `link.ld` are fixed (the cIOS maps depend on them). Bytes = `.init` + `.text` from the region start, `+next` build (`SDIO_HIGH_SPEED`):

| Module | Region | Used before | Free before | Used after | Free after |
| --- | --- | --- | --- | --- | --- |
| MLOAD | 0x2000 (8192) | 5716 | 2476 | 5400 | 2792 |
| FAT | 0x5000 (20480) | 18400 | 2080 | 18040 | 2440 |
| EHCI | 0x5000 (20480) | 16840 | 3640 | 16440 | 4040 |
| USBS | 0x3000 (12288) | 12272 | 16 | 11204 | 1084 |
| DIPP | 0x2000 (8192) | 6852 | 1340 | 6448 | 1744 |
| ES | 0x2000 (8192) | 3264 | 4928 | 2872 | 5320 |
| FFSP | 0x3000 (12288) | 7104 | 5184 | 6700 | 5588 |

The plain release build (no SD high speed) has 1436 free in USBS and 4392 in EHCI.

| Change | Bytes (USBS) | Why it does not change speed |
| --- | --- | --- |
| `cios-lib/syscalls.s`, `tools.s`: one section per stub (`.text.NAME`), so `--gc-sections` drops the stubs a module never calls (the whole file, 55 stubs of 8 bytes, was one section). All modules link it. | -396 (MLOAD -316, FAT -360, EHCI -400, DIPP -404, ES -392, FFSP -404) | The same instructions, only unused stubs go; no call path changes. |
| `libwbfs.c`: `wbfs_open_partition` divides through `wbfs_udiv`/`wbfs_sdiv` (`wbfs_div.c`, shift and subtract) instead of libgcc's `__udivsi3`/`__divsi3` (620 bytes) that nothing else in USBS needs. One shift replaces a division by the constant 0x8000. EHCI defines both with `/`, as it links the libgcc routines for `qtd_fill` and `USBStorage_Read/Write`. | -560 (EHCI +8 to +20) | Runs once per disc open (WBFS ioctl), never in a transfer. |
| USBS `usbstorage.c`: `__cycle` shares one `__data_phase` for the read and write chunk loops, and one recovery label for the four reset-and-retry exits. | -112 | Same calls in the same order per 16 KB piece; the per-piece code is the one loop, a flag picks the endpoint and the copy direction. |

Host tests added for the refactor (`tests/host/usbs`): direct-buffer write recovering from a STALL, and short data transfers (the module's residue paths) for a read and a write, bounce and direct. They pass on the old and the new `__cycle`. The tests already covered 16 KB chunking and bounce/direct both ways.

Not done: `-Os` is already on everywhere; Thumb is already on everywhere (only the syscall stubs, `start.s` and `.init` are ARM); there are no debug strings in release (`.rodata` is 196 bytes in the data region). The WBFS ioctls are live (USB Loader GX), so wbfs.c stays. Next candidates if room is needed again: `sdio_Startup` (952 bytes, cold), `wbfs_open_partition`'s reset-only branch (about 150 bytes, needs a compile-time switch in the shared lib).
